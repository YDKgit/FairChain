# JMeter 공부 노트 — 우리 부하 테스트가 어떻게 돌아가는가

발표 때 "부하 테스트를 어떻게 했나"를 설명할 수 있도록, JMeter의 개념을 우리 파일(`fairticket.jmx`)에 맞춰 정리한 글이다.
실행 방법과 측정 기록은 [README.md](README.md)에 있다.

## 1. JMeter가 하는 일

JMeter는 **가상 사용자를 여러 명 만들어 서버에 요청을 보내고, 걸린 시간과 성공 여부를 기록하는 프로그램**이다.

- 화면을 그리거나 버튼을 누르지 않는다. 브라우저가 서버에 보내는 요청(HTTP)만 그대로 흉내 낸다
- 서버 입장에서는 진짜 1,500명이 접속한 것과 같은 요청이 들어온다
- 가상 사용자 한 명은 프로그램 안의 **스레드 하나**다. 그래서 JMeter에서는 사용자를 "스레드"라고 부른다

요청이 가는 길은 실제 사용자와 같다.

```
JMeter → 예매 사이트(8080) → FairChain(8081) → 노드(9001~9003)
```

## 2. 핵심 생각: "한 사람이 할 일"을 적고, 사람 수만큼 복사한다

`fairticket.jmx`에는 **한 사람이 순서대로 할 일**만 적혀 있다. JMeter가 이것을 사람 수만큼 복사해 동시에 돌린다.

그런데 모두가 똑같은 요청을 보내면 안 된다(같은 아이디로 1,500번 로그인하게 된다). 그래서 요청 안에 **변수**를 넣는다.

```
{"loginId":"${loginId}", "password":"load1234"}
```

`${…}` 자리는 실행할 때 사용자마다 다른 값으로 바뀐다. `loginId`는 요청 직전에 실행되는 작은 스크립트(`회원 아이디 정하기`)가
"`load` + 내가 몇 번째 사용자인지"로 채운다.

| 가상 사용자 | 실제로 보내는 아이디 |
|---|---|
| 1번 | `load1` |
| 2번 | `load2` |
| 1500번 | `load1500` |

요청은 한 번만 적었지만 사용자마다 다른 아이디가 된다. 이것이 "몇 줄로 몇천 명"이 되는 원리다.

## 3. 화면(트리)의 아이콘이 뜻하는 것

`jmeter -t loadtest/fairticket.jmx`로 열면 왼쪽에 트리가 보인다. 접혀 있으면 **Options → Expand All**로 펼친다.
항목을 누르면 오른쪽에 내용이 나온다.

| 모양 | JMeter 이름 | 뜻 | 우리 파일의 예 |
|---|---|---|---|
| 톱니바퀴 | Thread Group (스레드 그룹) | 사용자 묶음. **몇 명이, 몇 초에 걸쳐 시작하는지**를 정한다 | `A. 예매 오픈 폭주` |
| 스포이트 | Sampler (샘플러) | 서버에 보내는 요청 하나 | `A-1 대기열 진입` |
| 네모 상자 | Controller (컨트롤러) | 조건·반복. "~이면", "~할 때까지" | `입장 허용까지 대기` |
| 공구 | Config (설정) | 여러 요청이 같이 쓰는 설정 | `HTTP 기본값`, `세션 쿠키` |
| 요청 아래 달린 것 | Pre/PostProcessor | 요청 전·후에 실행하는 작은 스크립트 | `좌석 고르기`, `대기열 상태 읽기` |
| 시계 | Timer (타이머) | 요청 전에 기다리는 시간 | 순번 확인 전 1초 대기 |

트리는 위에서 아래로 실행된다. 안쪽으로 들여 쓴 항목은 바깥 항목에 속한다.

## 4. 우리 시나리오 A를 한 줄씩 읽기

부하 테스트에서 쓰는 것은 `A. 예매 오픈 폭주` 하나다. 가상 사용자 한 명이 아래 순서로 움직인다.

| 단계 | 요청 | 하는 일 |
|---|---|---|
| A-0 로그인 | `POST /api/members/login` | 미리 만들어 둔 회원으로 로그인한다. 받은 쿠키는 그 사용자만 가진다 |
| A-1 대기열 진입 | `POST /api/queue/{공연}` | 줄을 선다. FairChain이 순번을 준다 |
| A-1 대기 순번 확인 | `GET /api/queue/{공연}/status` | **입장이 허용될 때까지 1초마다 반복**한다 |
| A-2 좌석 조회 | `GET /api/concerts/{공연}/seats` | 좌석 목록을 받는다. 붙어 있는 스크립트가 **빈 좌석 하나를 무작위로 고른다** |
| A-3 예매 | `POST /api/reservations` | 고른 좌석을 예매한다. 다른 사람이 먼저 잡았으면 A-2로 돌아가 다시 고른다(최대 5번) |
| A-4 내 티켓 확인 | `GET /api/tickets/{티켓}` | 블록체인 검증이 끝날 때까지 0.5초마다 확인한다(최대 60초) |

결과 표에 나오는 이름이 이 단계 이름이다. 이름 뒤에 설명이 붙는 경우가 있다.

| 결과 표의 이름 | 뜻 |
|---|---|
| `A-3 예매 — 선점 실패 (다시 고름)` | 같은 좌석을 다른 사람이 먼저 잡았다. **정상 동작**이라 오류로 세지 않는다 |
| `A-2 좌석 조회 — 매진이라 포기` | 입장했지만 빈 좌석이 없었다. 역시 정상이다 |
| `A-4 예매 후 블록체인 검증 완료까지` | 예매 성공부터 노드 검증이 끝날 때까지 걸린 전체 시간 |

### 나머지 시나리오

| 이름 | 확인하는 것 | 기본 인원 |
|---|---|---|
| `준비: 좌석 등록` | 운영자로 로그인해 모자란 좌석을 채운다. 본 측정 전에 한 번 실행된다 | 1 |
| `B. 같은 좌석 동시 예매` | 여러 명이 **같은 좌석 하나**를 동시에 예매한다. 한 명만 성공해야 한다 | 20 |
| `C. 매크로` | 한 회원이 쉬지 않고 요청을 보낸다. 초당 5번을 넘으면 차단되어야 한다 | 1 |
| `D. 둘러보기` | 로그인 없이 목록만 본다. 비교용 기준값 | 0 |
| `판정` | B에서 성공한 사람이 정확히 1명인지 마지막에 확인한다 | 1 |

우리 실행 스크립트는 B와 C를 0명으로 두고 A만 돌린다.

## 5. 사용자마다 따로 움직이게 하는 장치 세 가지

**① 쿠키를 따로 보관한다 (세션 쿠키)**
로그인하면 서버가 쿠키를 준다. `세션 쿠키 (스레드마다 따로)`가 이것을 사용자마다 따로 들고 있어서, 1,500명이 각자 로그인한 상태가 된다. 브라우저 1,500개를 따로 띄운 것과 같다.

**② 응답에서 값을 꺼내 다음 요청에 쓴다**
좌석 조회 응답에는 좌석 목록이 들어 있다. 요청 아래에 붙은 스크립트(`좌석 고르기`)가 그중 빈 좌석 하나를 골라 `seatId`라는 변수에 넣고, 다음 요청(예매)이 그 값을 쓴다.

```
A-2 응답: 좌석 목록  →  스크립트: 빈 좌석 하나 고름  →  A-3 요청: {"seatId": 고른 번호}
```

이 스크립트는 Groovy라는 언어로 적혀 있다(자바와 거의 같다).

**③ 조건과 반복으로 흐름을 만든다**
"입장이 허용될 때까지 반복", "예매에 성공했을 때만 검증 확인"은 컨트롤러가 한다. 그래서 사용자마다 걸리는 시간과 거치는 단계가 달라진다.

## 6. 몰리는 방식을 정하는 값 세 가지

같은 시나리오라도 **사람들이 어떤 간격으로 들어오는지**에 따라 결과가 크게 달라진다.

| 값 | 뜻 |
|---|---|
| `users` | 가상 사용자 수 |
| `rampUp` | 모든 사용자가 시작하는 데 걸리는 초. 1,500명에 150초면 0.1초에 한 명씩 시작한다 |
| `syncGroup` | "몇 명이 모이면 한꺼번에 보낼지". 0이면 전원이 모일 때까지 기다렸다가 동시에, 1이면 기다리지 않고 오는 대로 |

이 세 값의 조합으로 스크립트 세 개를 만들었다.

| 스크립트 | 방식 | 값 |
|---|---|---|
| `run-slow.sh` | 한 명씩 일정한 간격으로 | `syncGroup=1`, `rampUp` = 인원 × 간격 |
| `run-waves.sh` | 200명씩 묶어서 5초마다 | `syncGroup=200` |
| `run-multi.sh` | 1만 명이 같은 순간에 | `syncGroup=0` + 정해진 시각까지 대기 |

실제 예매 오픈은 "정각에 한꺼번에"에 가깝고, 평소 접속은 "한 명씩 꾸준히"에 가깝다. 둘 다 재는 이유다.

## 7. 값을 바꾸는 방법 (`-J`)

파일을 고치지 않고 실행할 때 값을 넣는다. 파일 안에는 `${__P(users,100)}`처럼 적혀 있는데, "`users`라는 값이 들어오면 그것을 쓰고, 없으면 100"이라는 뜻이다.

```
jmeter -n -t loadtest/fairticket.jmx -Jusers=1500 -JrampUp=150 -JconcertId=11
```

| 옵션 | 뜻 |
|---|---|
| `-n` | 창 없이 실행한다. **측정할 때는 반드시 이 방식** — 창을 그리는 데 자원을 쓰면 수치가 나빠진다 |
| `-t 파일` | 실행할 시나리오 파일 |
| `-l 파일` | 결과를 기록할 파일(`.jtl`) |
| `-J이름=값` | 시나리오에 넘기는 값 |

우리 스크립트(`run-*.sh`)는 이 명령을 알맞은 값으로 대신 쳐 주는 것이다.

## 8. 결과 읽는 법

JMeter는 요청 하나마다 한 줄씩 기록한다(`.jtl` 파일, 쉼표로 나눈 표). `summarize.py`가 이것을 단계별로 모아 보여 준다.

```
  10000 err=     0 avg=  1376ms max=  2848ms  A-1 대기열 진입
```

| 칸 | 뜻 |
|---|---|
| `10000` | 이 단계의 요청 수 |
| `err=0` | 실패한 요청 수 |
| `avg` | 평균 응답 시간 |
| `max` | 가장 오래 걸린 요청 |

표 아래에는 실패 이유가 건수와 함께 나온다. 이유에 따라 **누구의 문제인지**가 다르다.

| 실패 이유 | 뜻 | 누구의 한계인가 |
|---|---|---|
| `503` | 서버가 "지금 못 받는다"고 답했다 | 서버 |
| `BindException: Can't assign requested address` | 요청을 보낼 포트가 남아 있지 않다. 요청이 서버에 닿기 전에 실패했다 | **JMeter를 돌린 컴퓨터** |
| `SocketTimeoutException: Read timed out` | 보냈는데 정해진 시간 안에 답이 없었다 | 서버가 느리거나 컴퓨터가 과부하 |

`BindException`은 한 컴퓨터가 한 서버로 열 수 있는 연결이 약 16,000개라서 생긴다. JMeter와 서버를 같은 노트북에서 돌리면 1만 명부터 이 한계에 걸린다. 그래서 "오류 없이 잴 수 있는 것은 6천 명까지"라고 적었다.

## 9. 숫자를 믿으려면 지킬 것

- **창 없이 돌린다** (`-n`)
- **연달아 돌리지 않는다.** 큰 테스트 직후에는 포트가 덜 풀려 있다. 몇 분 쉬었다가 돌린다
- **깨끗한 공연에서 돌린다.** 스크립트가 돌릴 때마다 새 공연을 만드는 이유다. 회원 한 명은 한 공연에 한 장만 살 수 있어서, 같은 공연에서 다시 돌리면 앞사람이 전부 실패한다
- **진입 전 대기를 60초 넘게 잡지 않는다.** JMeter는 60초 넘게 쉰 연결을 버리고 새로 맺는다. 1만 명이 진입 순간에 한꺼번에 다시 연결하면 대부분 실패한다(2026-11-23에 실제로 겪음). 기본값 70초를 그대로 쓴다
- **같은 컴퓨터에서 잰 수치임을 밝힌다.** JMeter도 CPU와 메모리를 쓰므로, 서버만 따로 둔 경우보다 수치가 나쁘게 나온다

## 10. 시나리오를 고치고 싶을 때

`fairticket.jmx`는 손으로 만든 파일이 아니다. `build_jmx.py`가 만들어 낸다.

```
python3 loadtest/build_jmx.py        # fairticket.jmx 를 다시 만든다
```

- JMeter 창에서 고쳐 저장하면 다음에 위 명령을 돌릴 때 덮어써진다. **고칠 때는 `build_jmx.py`를 고친다**
- 파이썬으로 만든 이유: `.jmx`는 글자 수만 5만 자가 넘는 XML이라 손으로 고치기 어렵고, 같은 구성(로그인, 대기열 진입)을 A·B·C가 함께 쓰기 때문이다

`build_jmx.py`에서 볼 만한 곳

| 함수 | 내용 |
|---|---|
| `scenario_a()` | 4장의 표가 그대로 코드로 적혀 있다 |
| `enter_queue_and_wait()` | 대기열 진입과 "입장할 때까지 반복" |
| `PICK_SEAT` | 빈 좌석을 무작위로 고르는 스크립트 |
| `all_at_once()` | 여러 명이 모였다가 동시에 보내는 타이머 |

## 11. 발표에서 나올 만한 질문

| 질문 | 답 |
|---|---|
| 가상 사용자는 진짜 사용자와 뭐가 다른가요? | 화면을 그리지 않고 요청만 보냅니다. 서버가 받는 요청은 같습니다. 예매 사이트와 FairChain, 노드를 모두 거칩니다 |
| 1만 명이 정말 동시에 들어왔나요? | 미리 로그인해 두고 같은 시각에 진입 요청을 보냈습니다. 기록을 보면 1만 건이 0.6~0.9초 안에 몰려 있습니다 |
| 실패한 요청은 왜 생겼나요? | 대부분 부하를 만드는 쪽 컴퓨터의 연결 수 한계입니다. 서버에 닿기 전에 실패한 것이고, 서버가 거절한 것은 약 1%입니다 |
| 왜 노트북 한 대에서 쟀나요? | 장비가 그것뿐이었습니다. 그래서 수치는 보수적입니다. 부하 발생기를 다른 컴퓨터로 분리하는 것이 남은 일입니다 |
| 같은 좌석이 두 번 팔리지 않는다는 것은 어떻게 확인했나요? | 좌석 수와 예매 성공 수가 일치하고(600석에 600건), 같은 좌석을 20명이 동시에 예매하는 시나리오 B에서 성공이 정확히 1명입니다 |
| 매크로는 어떻게 흉내 냈나요? | 한 회원이 쉬지 않고 대기열 요청을 100번 보내게 했습니다. 초당 5번을 넘는 요청은 차단되는 것을 확인합니다 |

## 12. 용어

| 용어 | 뜻 |
|---|---|
| 스레드 (Thread) | 가상 사용자 한 명 |
| 스레드 그룹 | 같은 일을 하는 가상 사용자 묶음 |
| 샘플러 (Sampler) | 요청 하나. 결과 표의 한 줄이 된다 |
| 램프업 (Ramp-up) | 전원이 시작하는 데 걸리는 시간 |
| 생각 시간 (Think time) | 사람이 화면을 보고 누르기까지의 시간을 흉내 낸 대기 |
| `.jmx` | 시나리오 파일 |
