# 노드 속도 측정 기준

Raft 적용 전후를 **같은 조건**으로 비교하기 위한 기록입니다. 숫자는 PC마다 다르므로 **같은 표 안의 비율**을 봅니다.

## 측정 방법

- 도구: `scripts/bench_nodes.py` — FairChain 없이 노드에 기록을 **하나씩** 보내고, 확정 응답을 받은 뒤 다음 기록을 보냅니다
  (FairChain 대기 줄이 한 번에 1건씩 보내는 것과 같은 방식).
- 받는 노드가 거부하거나 2초(`fairchain.nodes.timeout`) 안에 답하지 않으면 FairChain처럼 다음 노드로 넘깁니다.
- 측정 전에 20건을 먼저 보내 JVM을 데웁니다(측정에서 뺌).
- 노드 저장소: H2 파일, `WRITE_DELAY=0` (커밋마다 디스크에 기록) — 시연 설정과 같습니다.

```cmd
python scripts\bench_nodes.py --urls http://localhost:9101,http://localhost:9102,http://localhost:9103 --records 300 --runs 3 --secret bench-secret
```

참고

- 11/06 측정(같은 PC, 300건 × 3회)은 10.2 건/s · 98 ms였습니다. 이번 값과 거의 같습니다.

## 2. Raft 방식 (`raft-node`)

### 2단계 직후, PC 1대 (2026-11-16, 위와 같은 PC · 같은 명령)

리더 층 3대(A1 · B1 · C1), 하트비트 1초 · 하트비트 시간 제한 4초, Raft 상태는 노드마다 SQLite 파일.

| 상황 | 기록 수 | 처리량 | 1건 평균 | 중간값 | 95% |
|---|---|---|---|---|---|
| 팔로워(노드1)에 보냄 → 리더에게 전달 (FairChain과 같은 방식) | 300건 × 3회 | **32.8 건/s** | **31.3 ms** | 17–32 ms | 52–74 ms |
| 리더에 바로 보냄 | 300건 × 3회 | 56.6 건/s | 17.7 ms | 12–13 ms | 34–40 ms |

| FairChain을 거친 측정 | 좌석 발행 200건 | 예매 200건 | 체크인 검증 |
|---|---|---|---|
| `raft-node` | 11.9 s · 16.8 건/s · 59 ms/건 | 8.9 s · 22.5 건/s · 44 ms/건 | 정상 20/20 VERIFIED · 위조 → TAMPERED |

리더 장애

- 통합 테스트(`NodeClusterTest`): 리더 노드를 끈 뒤 새 리더까지 **4.1초**.
- 실제 프로세스: 리더를 `taskkill /F`로 강제 종료한 뒤, FairChain처럼 0.5초마다 다시 보내 **4.7초** 만에 다음 기록이 확정됨
  (새 리더 A1, 임기 2). 목표 "5초 안에 새 리더"(미정사항 7번)를 PC 1대에서는 만족.
- 강제 종료한 노드를 다시 켜면 디스크의 Raft 상태(임기 · 로그)로 복원하고 빠진 블록을 따라잡아 3대의 마지막 해시(1821번 블록)가
  같아졌다. 1000건마다 스냅샷을 만들고 로그 앞부분을 자르는 것도 이 과정에서 함께 확인됐다.

해석

- 빨라진 이유: 블록 1개에 왕복 1번(Raft 표준) — 리더가 팔로워 2대에 **동시에** 보내고 과반이 저장하면 확정. 예전에는
  제안 · 결정 · 확정 3단계를 이웃마다 **차례로** 호출했다(블록당 HTTP 7번, 디스크 커밋 약 12번).
- 팔로워에 보내면 리더에게 한 번 더 넘기므로 리더에 바로 보낼 때보다 느리다. FairChain은 리더를 몰라도 된다는
  결정(미정사항 5번)을 지키는 비용이다.

### 3단계 직후 (블록 서명 추가), PC 1대 (2026-11-16)

| 상황 | 처리량 | 1건 평균 |
|---|---|---|
| 팔로워(노드1)에 보냄, 300건 × 3회 | 31.0 건/s | 32.7 ms |
| FairChain: 좌석 발행 200건 / 예매 200건 | 16.9 건/s / 20.2 건/s | 59 ms / 50 ms |

- 노드마다 확정 블록을 쓸 때 Ed25519로 서명한다. 서명 전(32.8 건/s)과 차이는 측정 오차 안이다.
- 켤 때 체인 전체 검사(해시 + 블록마다 서명 확인): 블록 920개에 약 2초.

### 4단계 직후 (팀원 추가), PC 1대 · 프로세스 9개 (2026-11-16)

리더 층 3대(A1 · B1 · C1) + 팀마다 팀원 2대(A2 · A3 · B2 · B3 · C2 · C3). 시연 구성(PC 1대 = 팀 1개)을 PC 한 대에 모은 것.

| 상황 | 처리량 | 1건 평균 |
|---|---|---|
| 팔로워(노드1)에 보냄, 300건 × 3회 | 25.4 건/s | 39.5 ms |

- 프로세스 3개일 때(31.0 건/s)보다 느린 것은 팀원 JVM 6개가 같은 CPU · 디스크를 쓰기 때문이다. 팀원에게 보내는 일은 확정과
  따로 돌아서 FairChain 응답을 기다리게 하지 않는다. PC 3대에서는 PC마다 프로세스 3개다.
- 측정이 끝나고 0.4초 안에 9대의 마지막 블록 해시가 모두 같아졌다.
- 리더 장애 (`python scripts/raft_nodes.py failover --times 8`, 2026-11-17): 리더를 강제 종료 → 새 리더까지
  **평균 4.36초 · 최대 4.55초**, 다음 기록 확정까지 최대 4.63초 (하트비트 1초 · 시간 제한 4초 · 노드마다 선거 시간 제한 +0~500ms).
  8회 중 7회는 MicroRaft가 스스로, 1회는 리더 장애 감지 보완이 선거를 시작했다.
  주의: 끈 노드에도 상태를 물으면 Windows에서 닫힌 포트 연결이 약 2초씩 걸려 측정이 8초대로 늘어난다 — 도구는 살아 있는 노드만 본다.
- 팀 리더 A1을 강제 종료 → 팀원 A2 · A3는 B1의 사본을 받아 계속 따라옴. A1을 다시 켜면 다시 A1의 사본을 받고 9대가 같아짐.

### 9단계 측정 방법 — PC 3대 (Wi-Fi), 같은 커밋 · 같은 명령

PC1 · PC2 · PC3의 IP를 `IP1` · `IP2` · `IP3`라고 하면:

1. 지금 방식 (`demo-page`, 비교 기준) — 각 PC에서 노드 1대
   ```
   set NODE_PORT=9001& set NODE_SECRET=bench-secret& set NODE_PEERS=http://IP2:9001,http://IP3:9001& java -jar node\build\libs\node-0.0.1-SNAPSHOT.jar
   ```
   (PC2 · PC3은 NODE_PEERS에 나머지 두 IP). 그다음 아무 PC에서:
   `python scripts\bench_nodes.py --urls http://IP1:9001,http://IP2:9001,http://IP3:9001 --records 300 --runs 3 --secret bench-secret`
2. Raft (`raft-node`) — PC마다 팀 하나 (리더 층 1대 + 팀원 2대):
   ```
   python scripts\raft_nodes.py start --fresh --team A --host IP1 --secret bench-secret --leaders A1=http://IP1:9001,B1=http://IP2:9001,C1=http://IP3:9001
   ```
   (PC2는 `--team B --host IP2`, PC3은 `--team C --host IP3`, `--leaders`는 셋 다 같음). 처리량은 1번과 같은 `bench_nodes.py` 명령.
3. 리더 장애 (Raft만) — 한 PC에서 `python scripts\raft_nodes.py watch-failover`를 켜 두고, 리더가 있는 PC에서
   `python scripts\raft_nodes.py stop <리더 ID>` → 새 리더까지 · 다음 기록 확정까지 시간이 찍힌다. 끈 노드는 `up <ID>`로 켜고
   10초쯤 기다린 뒤 되풀이 (5번 이상). 하트비트 시간 제한 3초도 재 보려면 2번 `start`에 `--heartbeat-timeout 3`.
4. 방화벽: 9001 · 9011~9019 (팀 B 9021~, 팀 C 9031~은 PC 1대 구성일 때만) 를 같은 Wi-Fi 안에서 열어 둔다.
