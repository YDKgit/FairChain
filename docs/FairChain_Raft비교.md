# 지금 노드 구조(A안) vs Raft 안 비교

작성: 윤도균 · 2026-11-06
대상: 이고르 님 「Raft 방식 검토 정리」 문서 + 현재 `demo-page` 브랜치 코드
(`node/.../service/NodeService.java`, `fairchain/.../block/requester/BlockRecordRequester.java`)

---

## 0. 지금 A안은 실제로 이렇게 동작한다

- FairChain(`BlockRecordRequester.submitRecord`)은 노드 목록 순서대로 시도해서, **처음으로 응답하는 노드 한 대**에 기록을 보낸다. 보통 노드1이 받고, 실패하면 다음 노드로 넘어간다.
- 그 노드가 **제안자(사실상 임시 리더)**가 되어 나머지 노드에 3단계로 보낸다(`completeRound`).
  1. 제안(proposal) → 과반이 찬성하면
  2. 확정 결정(decision)
  3. 확정(confirm)
- 받는 노드끼리는 서로 다시 보내지 않는다. 그래서 블록 하나에 메시지는 **약 3 × (n−1)개 = O(n)**이다. **n²가 아니다.**
- 느린 실제 이유는 두 가지다.
  - 이웃 노드에 **하나씩 차례로** 보낸다(`for (String peer : peers)`, 동시에 보내지 않음).
  - **왕복이 3번**이다.
  - 그래서 측정값이 노드 3대 61ms → 10대 185ms처럼 노드 수에 비례해서 늘었다(`scripts/bench-nodes.sh`, 같은 맥).

## 1. 항목별 비교

| 항목 | 지금 A안 (`demo-page`) | Raft 안 |
|---|---|---|
| 누가 기록을 제안하나 | FairChain이 목록 순서대로 고른 노드(보통 노드1). 선거 없음 | 투표로 뽑은 리더. 임기(term)와 하트비트가 있음 |
| 블록 하나 확정에 드는 왕복 | 3번 (제안 → 결정 → 확정), 노드에 차례로 보냄 | 1번 (보내기 → 저장했다는 답). 확정 사실은 다음 메시지에 실어 보냄 |
| 메시지 수 | 약 3(n−1) | 약 2(n−1) |
| 확정 기준 | 전체 명단의 과반 (`quorum = (명단 크기)/2 + 1`) | 전체 명단의 과반 (**같음**) |
| 꺼졌던 노드 따라잡기 | 노드가 5초마다 다른 노드에서 **가져옴** (`synchronize`) | 리더가 빠진 블록을 **보내 줌** |
| 리더(제안자)가 죽으면 | FairChain이 다음 노드로 넘어감. 남은 제안은 다음 제안자가 마무리 (`settlePending`) | 150~300ms 안에 새 리더 선거 |
| 노드 추가 | `NODE_PEERS` 수정 후 재시작. 바뀌는 순간 노드마다 과반 계산이 달라질 수 있음 | learner로 붙인 뒤 1대씩 투표 노드로 올림 (안전) |
| 거부 이유 | `true/false`만 돌려줌 (`peerPost`) | 이유 코드 (STALE_TERM, BEHIND, DIVERGED 등) |

## 2. 변조 대응 비교

### 2-1. 제안된 규칙 4개 중 3개는 이미 있다

| Raft 안 규칙 | 지금 코드 |
|---|---|
| 1) prevBlockHash가 맞을 때만 받기 | **있음.** `validProposal`이 번호 · 이전 해시 · 블록 해시 · 버전 증가를 확인 |
| 2) 자체 점검, 깨지면 투표 · 제안 중단 | **있음.** `LedgerMaintenance`가 5초마다 `maintain`, 깨지면 `chainBroken`으로 투표 · 제안에서 빠짐 |
| 3) 확정 블록은 덮어쓰지 않음 | **있음.** 덮어쓰거나 지우는 기능이 아예 없고 뒤에 붙이기만 함 (`appendCommitted`) |
| 4) 리더 전자서명 (Ed25519) | 없음 (새 기능) |

### 2-2. 경우별 비교

| 경우 | 지금 A안 | Raft 안 |
|---|---|---|
| (1) 1대 변조, 해시 재계산 안 함 | 점검에서 걸려 투표에서 빠짐. 복구는 사람이 `--wipe` | 같음. 복구는 "망가진 곳부터 지우고 다시 받기"로 자동화 |
| (2) 변조하고 해시까지 재계산 | 점검은 통과하지만 새 블록을 못 받아 **뒤처진 채 멈춤**. 자동 복구 없음 | 공통 지점을 찾아 잘라내고 다시 받음 (**새로 생기는 기능**) |
| (3) 제안자(리더) 변조 | 다른 노드가 반대 → 과반 실패 → FairChain이 다음 노드로 넘어감 | 팔로워가 거부 → "리더 이상"으로 보고 재선거 (**추가로 만들어야 하는 규칙**) |
| (4) 3대 중 2대 변조 | 못 막음 | 못 막음 (서명이 있으면 리더 키 없이는 위조 불가) |

## 3. Raft 안에서 확인이 필요한 점

1. **MicroRaft로 규칙 1 · 3과 (3)번 재선거를 넣을 수 있는지.**
   규칙 1 · 3, (3)번 재선거는 Raft가 "블록을 받을지 말지", "리더를 바꿀지"를 정하는 **내부 동작을 고치는** 일이다. MicroRaft는 확정된 뒤에 결과를 넘겨주는 구조로 보여서, 받기 전에 내용을 검사해 거부하는 부분을 끼워 넣을 수 있는지 확인이 필요하다.
   안 된다면 "MicroRaft를 가져다 쓴다"가 아니라 **"Raft를 직접 구현한다"**가 되고 작업량이 크게 달라진다. (추정. MicroRaft 코드는 아직 확인하지 않음)
2. **(2)번 경우의 노드가 리더로 뽑힐 수 있다.**
   Raft 선거는 로그 길이와 임기만 보고 내용은 보지 않는다. 해시까지 재계산한 변조 노드는 자체 점검을 통과하므로 리더가 될 수 있고, 그러면 다른 노드들이 계속 거부하면서 기록이 멈출 수 있다. (3)번 규칙(거부가 쌓이면 리더 교체)이 반드시 같이 있어야 한다.
3. 나머지(과반은 전체 명단 기준, 홀수 권장, learner, BFT는 4대부터 의미 있음, 거부 이유 코드 필요)는 정확하다.

## 4. 정리와 제안

- 지금 A안은 이미 **"임시 리더 + 과반 확정 + 해시 체인 검사"** 구조라서 Raft와 생각보다 가깝다.
  없는 것은 **리더 선거, 안전한 노드 추가, (2)번 경우 자동 복구, 거부 이유 코드**다.
- 속도 문제는 n²가 아니라 **차례로 보내기 + 왕복 3번** 때문이다. Raft로 갈아타지 않아도 아래만으로 상당히 빨라질 것으로 예상한다(= 이고르 님 문서의 "1단계 개선").
  1. 이웃 노드에 **동시에** 보내기
  2. 결정 · 확정 단계를 합쳐 **왕복 3번 → 2번**
  3. 거부 이유 코드 추가

### 제안하는 순서
1. 지금 코드에 1단계 개선을 넣고 속도를 다시 잰다 (`bench-nodes.sh`로 3대 · 5대 · 10대).
2. MicroRaft에 내용 검사(규칙 1 · 3)를 끼울 수 있는지 확인한다.
3. 끼울 수 있으면 Raft로 가고, 어려우면 지금 구조에 **리더 선거와 노드 추가 절차만 Raft 방식으로** 더한다.
